# DEC0004 | Run tests by launching the test project's executable

## Status

| Date | Status | Note | Related minutes |
|---|---|---|---|
| 2026-08-31 | Accepted | | |

## Context

An xUnit 4 test project builds to an executable. Investigating how that executable reaches Microsoft
Testing Platform produced the finding that drove this decision. The entry point generated by
`xunit.v3.mtp-v2` is, in substance:

```csharp
if (args.Any(a => a == "--server" || a == "--internal-msbuild-node"))
    // Microsoft Testing Platform host
else
    // xUnit in-process console runner
```

So the MTP host is reachable **only** through JSON-RPC server mode (`--server --client-port N`, which
throws without a port) or through MSBuild (`dotnet test`). Simply running the executable uses xUnit's
own in-process console runner.

Three options, all measured:

| Option | Cost per run | Exit code on failure |
|---|---|---|
| Launch the executable directly | **~0.6 s** | 1 |
| `dotnet test --no-build` | ~1.5 s | 2 |
| `--server --client-port N` (JSON-RPC) | not measured | protocol |

The project owner was asked to arbitrate what "Microsoft Testing Platform 2 only" means, and chose:
the *projects under test* must be xUnit 4 projects; KillMutants itself need not speak the MTP
protocol. That constraint has since been restated more precisely. The foundation is **xUnit 4 and
modern .NET only**, with no VSTest or legacy-runner compatibility. MTP 2 is part of the ecosystem we
target — an xUnit 4 project may run on it, and we handle that — but it is not an architectural
constraint. The rule is to take the simplest, most reliable and fastest xUnit 4 execution path for
the job, and to introduce direct MTP coupling only when a concrete need justifies it and xUnit 4
cannot already meet it.

Both `dotnet test` and `dotnet build` copy the pristine assembly back over the test project's output.

The xUnit console runner exits **0** when a filter matches zero tests. Its result XML carries
`total`, `passed`, `failed`, `errors` and `skipped`.

The generated entry point has two shapes, inverted by the MSBuild property
`UseMicrosoftTestingPlatformRunner`. This was found after this record was first written, by an
adversarial review of the implementation:

```csharp
// default                                   // UseMicrosoftTestingPlatformRunner=true
if (--server || --internal-msbuild-node)     if (-automated || @@)
    MTP host;                                    xUnit console runner;
else                                         else
    xUnit console runner;                        MTP host;
```

On a project using the second shape, our arguments reached the Microsoft Testing Platform host, which
rejected them (`Unknown option '--noLogo'`), **exited 5 and wrote no result file** — aborting the
whole run. KillMutants was simply unusable on such projects. `-automated` selects the xUnit console
runner under *both* shapes.

## Decision

In this context, we run a project's tests by launching its test executable as a child process and
reading the outcome from the structured result file (`-result-xml`), using neither `dotnet test` nor
an MTP JSON-RPC client.

## Rationale

It is the fastest option, by 2.5x over `dotnet test`, on the operation that dominates total run time.

It takes no dependency on any xUnit or MTP package: the coupling is a command-line contract, confined
to `KillMutants.Testing.XUnit`. Under the restated foundation — the simplest, most reliable and
fastest xUnit 4 path, with MTP coupling only where a concrete need demands it — launching the
executable is not a pragmatic compromise against a stated constraint; it is simply the right path.

Injection stability follows from the same choice. `dotnet test` and `dotnet build` both copy the
pristine assembly back over the mutant, so neither may run once a mutant is in place; launching the
executable directly is what makes injection hold.

The outcome must be read from the result counts rather than the exit code, because the console runner
exits 0 when a filter matches zero tests. A tool trusting the exit code would report such a mutant as
`Survived`; reading `total`, `passed`, `failed`, `errors` and `skipped` makes a run that executed no
tests an error rather than a survival.

## Alternatives considered

### Alternative 1 — `dotnet test --no-build`

* **Description:** reach the test project through MSBuild, as the ordinary .NET workflow does.
* **Why rejected:** ~1.5 s against ~0.6 s per run, on the operation that dominates total run time —
  and it copies the pristine assembly back over an injected mutant, which makes it unusable here
  whatever its cost.

### Alternative 2 — MTP server mode over JSON-RPC

* **Description:** speak Microsoft Testing Platform's protocol directly (`--server --client-port N`),
  which is the only other way to reach the MTP host.
* **Why rejected:** the project owner arbitrated that KillMutants itself need not speak the MTP
  protocol, and the cost was not even measured because the simplest reliable xUnit 4 path already
  does the job. `ITestRunner` remains the seam where a server-mode implementation would be added if a
  concrete need appears.

## Consequences

### Positive

* The fastest option, by 2.5x over `dotnet test`, on the operation that dominates total run time.
* No dependency on any xUnit or MTP package; the coupling is a command-line contract confined to
  `KillMutants.Testing.XUnit`.
* The runner options we will need later already exist: `-stopOnFail` (a mutant is killed by the first
  failing test), `-list tests /json` (test discovery, M4), `-id <uid>` (running one test case, for
  test-to-mutant mapping in M5).

### Negative

* `dotnet test` and `dotnet build` must never run after a mutant is injected.
* We give up MTP's richer per-test event stream. If M5 shows that test-to-mutant mapping genuinely
  needs it, `ITestRunner` is where a server-mode implementation would be added — a deliberately thin
  seam, not a plugin system.

### Risks

* What a test application does with a command line is a property of the project that produced it, not
  of the framework version. A project shape we have not seen can reject our arguments the way the
  second entry-point shape did: exit 5, no result file, and the whole run aborted.

### Follow-up actions

* Pass `-automated` on every run and keep it first in the argument list: it is the one flag that
  selects the xUnit console runner under both entry-point shapes.
* Keep the end-to-end regression test that builds a fixture with
  `UseMicrosoftTestingPlatformRunner=true` and fails with `Unknown option '--noLogo'` if the flag is
  removed.
